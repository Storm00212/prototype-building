Before you open your editor

Build the smallest useful thing.

A prototype is not the finished product. It is a believable, testable demonstration that the core idea can work.

01 / PROBLEM
◎

Who has the problem?

Name one real user and one painful task. Avoid solving every problem in the sector at once.

02 / MAIN FLOW
↗

One complete journey

For example: submit a report → see confirmation → view that report in a dashboard.

03 / PROOF
✓

Show evidence

Use a real working flow, sample data clearly labelled as sample, and a short demo script.

Weekend rule: a simple feature that works from start to finish beats ten impressive buttons that do nothing.
Pick the simplest stack your team knows

What are we actually building?

A · WEB FRONTEND

React / Vite

Good for a fast browser-based prototype. Build the interface and call an API when data needs to be shared or saved.

Host: Render Static Site

B · FULL-STACK WEB

Next.js

Useful when the team wants pages and server-side routes in one project. Confirm which features need a Node-capable deployment.

Host: Render Web Service or another compatible host

C · MOBILE APP

React Native / Expo

Build an installable mobile experience. A web preview can help during development, but native device features need device testing.

Share: Expo preview / build

Important hosting distinction: a Render Static Site serves files such as HTML, CSS, JavaScript, and built frontend assets. It does not run your Express server or host a database. Deploy the Node API separately as a Web Service, and use a managed database.
Spend 20 minutes planning to save 2 hours

Agree on the demo contract.

Write one sentence

“[User] can [do task] so that [useful outcome].” If the team cannot agree on this, pause coding.

Draw the happy path

List the exact 3–5 actions a judge should be able to complete. Build these first.

Choose what is real

Mark features as working, simulated, or planned. Never present mock results as validated clinical or scientific findings.

Set a cut-off

Freeze new features before the demo. Reserve time for testing, deployment, and fixing the most visible bugs.

Problem report flow

Set up people before setting up packages

Give every person a clear lane.

FRONTEND

Interface owner

Pages, forms, validation messages, loading states, mobile layout, and API calls.

BACKEND

API owner

Routes, request validation, business rules, error responses, and database access.

DATA

Database owner

Tables or collections, fields, relationships, seed data, and safe access rules. One person can share this role with backend.

INTEGRATION / QA

Flow owner

Connects the parts, tests the full journey, tracks bugs, checks the deployed link, and prepares the demo.

One person can hold more than one lane. What matters is that every task has an owner and the team agrees on the interface between parts.
Local machine setup

Check the basics first.

Create a React + Vite frontend
npm create vite@latest client -- --template react
cd client
npm install
npm run dev

Open the local URL printed in the terminal. Keep that terminal running while you develop. If you choose TypeScript, use the react-ts template instead.

If the project already exists, do not recreate it. First read its README, inspect the package scripts, install dependencies, and run it before changing files.
Team workflow

Git is your undo button and teamwork tool.

Start a repository
git init
git add .
git commit -m "Initial working version"
git branch -M main
git remote add origin YOUR_REPOSITORY_URL
git push -u origin main

If the repository already exists, clone it instead of running git init in a random folder.

Safe daily routine

Pull before starting

git pull brings in the latest shared work.

Work in a branch

git switch -c feature/report-form

Commit a small change

git add . then git commit -m "Add report form"

Push and review

git push -u origin feature/report-form; merge after checking the change.

Never commit: .env files, API keys, passwords, database credentials, private user data, or production dumps. Add secrets to .gitignore and the hosting provider's environment settings.
Frontend and backend can work in parallel

Agree on the shape of the data.

Before both sides code independently, agree on the URL, method, fields, and response. This prevents the frontend expecting reportId while the backend returns id.

Frontend sequence

Build screens in the order users need them.

01

Page skeleton

Header, navigation, main content, and a layout that works on a phone.

02

Static content

Use sample objects to design the screen before the API is ready.

03

Form states

Empty, typing, invalid, submitting, success, and failure states.

04

Connect API

Replace sample data with a real request and show errors clearly.

05

Small-screen test

Check narrow width, long text, keyboard overlap, and tap targets.

06

Polish last

Spacing, motion, icons, and colour come after the main flow works.

A button must either do something meaningful or be visibly marked as “coming soon”. A dead button is a bug, even if the design looks good.
Node + Express API

Keep the backend boring and predictable.

Create a minimal API folder
mkdir server
cd server
npm init -y
npm install express cors dotenv
npm install --save-dev nodemon

If using TypeScript, add your chosen TypeScript tooling and types. Don't mix TypeScript and plain JavaScript setup instructions blindly.

Example server.js
require("dotenv").config();
const express = require("express");
const cors = require("cors");

const app = express();
app.use(cors({
  origin: process.env.CLIENT_ORIGIN
}));
app.use(express.json());

app.get("/api/health", (_req, res) => {
  res.json({ status: "ok" });
});

const port = process.env.PORT || 5000;
app.listen(port, "0.0.0.0", () => {
  console.log(`API listening on ${port}`);
});
This example uses CommonJS. If your package has "type": "module", use import syntax instead. Don't paste both module styles into the same file.
Request in · response out

Validate at the backend boundary.

A route should answer four questions

What came in?

Read URL params, query values, and JSON body.

Is it valid?

Check required fields, types, lengths, and allowed values.

What should happen?

Apply the rule and call the database layer.

What should go back?

Return a clear status code and predictable JSON.

Example error responses
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Title is required"
  }
}
200Request succeeded
201Something was created
400Invalid input
401 / 403Not signed in / not allowed
404Not found
500Unexpected server problem
Never trust frontend validation alone. Anyone can send a request without using your interface. Validate on the server too, and never return passwords, private tokens, or raw database errors.
Store only what the prototype needs

SQL or NoSQL? Choose by data shape.

▦

SQL · PostgreSQL / MySQL

Great when records relate to each other and you want clear rules. Tables, columns, constraints, and joins help keep data consistent.

Example: users, reports, report_updates, locations.

◇

NoSQL · MongoDB

Useful when records are document-shaped and their fields vary. Plan the document shape and indexes instead of treating it as “no structure”.

Example: flexible submissions with nested metadata.

Good database habits
  • Use environment variables for connection strings.
  • Use parameterized queries or a safe ORM.
  • Store timestamps consistently.
  • Validate and constrain important fields.
  • Keep demo data clearly identifiable.
Avoid these traps
  • Putting the database password in frontend code.
  • Connecting from a browser directly to a private database.
  • Assuming a local database exists in production.
  • Deleting or resetting production data during debugging.

Connect one feature all the way through.

Form in browser
→
fetch() request
→
Node API
→
Database
Frontend example
const API_URL = import.meta.env.VITE_API_URL;

async function loadReports() {
  const response = await fetch(`${API_URL}/api/reports`);
  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }
  return response.json();
}

In a Vite app, define VITE_API_URL in the local .env. Anything prefixed with VITE_ is visible to the browser — never put secrets there.

Check these when connecting
CORS is not authentication. It controls which browser origins may read responses; it does not stop direct API calls from scripts or tools.
Extra care for health-related ideas

Keep the demo safe and honest.

PRIVACY

Use dummy data

Do not collect real patient names, phone numbers, diagnoses, or records just to make the prototype look realistic.

ACCESS

Limit who can see what

Check permissions on the backend. Hiding a button is not access control.

CLAIMS

Explain limitations

Label AI output as experimental. Do not call it a diagnosis or validated prediction without proper evidence and review.

Never do this: upload real sensitive health data into a public demo, log passwords or tokens, commit secrets, or expose a database to the open internet without appropriate controls.
For a competition: use fictional names and generated examples, show a clear privacy note, and explain what would be needed before a real-world pilot.
Testing is a build step, not a final ceremony

Test the whole journey.

LEVEL 1

Manual checks

Click every visible control. Submit valid and invalid forms. Refresh the page. Try a narrow screen.

LEVEL 2

API checks

Use Postman, Insomnia, or curl. Test missing fields, wrong IDs, empty lists, and server errors.

LEVEL 3

End-to-end check

Start from a fresh browser session and complete the exact flow you will show the judges.

Example API smoke test
curl -i https://YOUR-API.onrender.com/api/health

Replace the example host with your deployed API URL. Expect a successful HTTP status and the JSON health response.

Browser debugging checklist
When it breaks, narrow the problem down

Debug with evidence, not random edits.

Reproduce it

Write down the exact action and what you expected versus what happened.

Read the first useful error

Check terminal output, browser console, Network tab, and server logs. Fix the earliest real error first.

Find which layer failed

Does the page render? Is a request sent? Does the API respond? Does the database query work?

Change one thing

Test again after each fix. Avoid changing five files at once because you will not know which change helped.

SymptomFirst thing to check
Blank pageBrowser console, import paths, component errors
404Exact route, base URL, route prefix, deployed build
500Backend logs and database connection
CORS errorExact origin, protocol, allowed methods/headers
Works locally onlyEnvironment variables, build command, production URL
Database timeoutCredentials, network access, provider status, connection limits
Module not foundDependency installed, filename case, package script
Deployment path A · static frontend

Put the frontend on Render.

Push working code to GitHub

Make sure the app runs locally and your latest commit contains the files you intend to deploy.

Create a Static Site

In Render, choose New → Static Site, connect the repository, and select the correct branch.

Set build details

For a Vite app in the repository root: Build Command npm install && npm run build; Publish Directory dist. If the frontend is in client, set the root directory to client or adjust commands accordingly.

Add public frontend config

Set VITE_API_URL to your deployed API origin, e.g. https://your-api.onrender.com. Trigger a new deploy after changing build-time variables.

Open the live URL

Test the full flow on the deployed site, not only the local preview. Check Console and Network tabs.

If your app uses React Router with client-side routes, configure a rewrite to serve /index.html for page routes. Do not rewrite API routes to the frontend.
Deployment path B · Node API

Deploy the API as a Web Service.

Create a Web Service

Connect the backend repository or monorepo folder. Select the branch and set the root directory correctly.

Set commands

Use the install and start commands that match your project. For example, install with npm install and start with npm start if the package script exists.

Listen on the assigned port

Use process.env.PORT, not a hard-coded port only. Bind to 0.0.0.0 where required by the platform.

Set environment variables

Add database URL, allowed client origin, and any required server secrets in Render's Environment settings.

Verify health route

Open /api/health on the live API and inspect deployment logs if it fails.

Production config example
NODE_ENV=production
CLIENT_ORIGIN=https://your-frontend.onrender.com
DATABASE_URL=provided-in-host-settings
Do not paste real credentials into slides, source code, chat screenshots, or GitHub. Set secret values privately in the hosting dashboard.

Hosting plan behaviour, sleep/cold starts, quotas, and supported runtimes can change. Check Render's current documentation and your service dashboard before the event.

Local is not production

Connect a managed database.

1. Create it

Use a managed PostgreSQL service or MongoDB Atlas project. Keep the database in a suitable region when practical.

2. Add credentials privately

Copy the connection string into the backend service's environment variables. Never into React code.

3. Test a real write

Create a sample record through the API, read it back, and verify the deployed UI displays it.

Common database failures
  • Wrong password or database name.
  • Missing network/IP allow-list access.
  • SSL requirement not configured.
  • Schema or migration was never run.
  • Provider free tier or connection limit reached.
Before demo day
  • Seed a small, predictable set of fake records.
  • Confirm records survive a page refresh.
  • Know how to reset demo data safely.
  • Have a screenshot or local fallback if connectivity fails.
Do not depend on a local SQLite file or local database running on your laptop unless you have deliberately designed and tested that deployment arrangement.
Fast fixes for common launch-day problems

Deployment fails? Check these in order.

ProblemLikely causeWhat to do
Build command failsWrong root folder or missing scriptCheck package.json, root directory, lockfile, and build logs.
Deploy succeeds, page is blankRuntime error or wrong asset pathOpen browser Console and Network; verify publish directory is dist for Vite.
Frontend can't reach APILocal URL still configured, CORS, API downInspect request URL; update VITE_API_URL; allow the exact site origin.
API starts then exitsMissing env var, bad start script, crashRead service logs from the first error and confirm the process binds to PORT.
Refresh gives 404SPA route not rewrittenAdd the static-site rewrite for frontend routes.
Works for one teammate onlyUncommitted files or machine-specific configCheck Git status, lockfile, environment setup, and clean install.
Useful rule: reproduce locally, fix, commit, push, wait for the new deploy, then retest the live URL. A local fix does not update the deployed site until the new build finishes.
Make the demo easy to follow

Rehearse a 90-second story.

0–15 SEC

The problem

Who experiences it, what goes wrong today, and why that matters.

15–65 SEC

The live flow

Show the main action, the system response, and the result saved or produced.

65–90 SEC

What is next

Explain what is working now, what is simulated, and what needs validation next.

If the internet drops

Keep the story alive.

Have a short local demo, a recording of the exact flow, and screenshots of the result. Be honest if you switch to a backup. Never pretend a video is a live system.

Before you call it ready

The ship checklist.

If a checklist item is not done, decide whether to fix it, remove the feature from the demo, or clearly explain the limitation. Don't hide a broken flow behind a polished landing page.
